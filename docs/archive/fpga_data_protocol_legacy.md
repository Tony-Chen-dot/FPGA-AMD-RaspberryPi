# FPGA / ARM 到树莓派的数据接入说明

## 1. 现在这套链路怎么分

这套系统故意把“视频”和“结构化结果”分开：

- `FPGA/ARM -> 树莓派`
  - 通过 `RJ45 以太网`
  - 推荐向 `FastAPI` 发送 `HTTP multipart/form-data`
  - 接口：`POST /api/device/ingest`

- `树莓派 -> 浏览器`
  - 视频：`MJPEG`
  - 推理框、统计、最近记录、历史数据：`WebSocket`

这样做的原因是：

- 浏览器可直接显示 `MJPEG`，树莓派无需再次进行视频编解码
- 板端不必直接实现最复杂的浏览器媒体协议
- 推理框和视频分离后，前端更好做比赛展示

## 2. 哪些数据是实时的，哪些数据来自数据库

### 实时层

- 最新视频画面
- 当前帧的框、类别、置信度
- 设备在线状态
- 最近一条结果

这些数据在新包到达时会立刻刷新，所以看起来会“跳”。  
这不是数据库轮询，而是“板端来一包，页面更新一包”。

### 历史层

- 最近 3 次推理图片
- 历史记录表
- 缺陷分布
- 趋势图
- 良率统计

这些内容会在树莓派收到新结果后先写入 `SQLite`，然后再从数据库整理成页面所需的数据结构。

一句话说：

- `视频和当前框`：偏实时
- `最近 3 次、统计图、历史表`：基于数据库沉淀

## 3. 板端最推荐的接入方式

### 方式 A：一张图 + 一条结果一起上传

接口：

```text
POST /api/device/ingest
```

请求类型：

```text
multipart/form-data
```

字段：

- `payload`：JSON 字符串
- `frame`：JPEG 图片

这是最推荐的方式，因为：

- 一次请求就把当前帧和当前推理结果对齐了
- 页面可以直接显示“最近三次推理图片”
- 数据库存档和页面展示最一致

### 方式 B：只上传推理结果

接口：

```text
POST /api/device/result
```

请求类型：

```text
application/json
```

适合：

- 板端暂时还不方便上传图片
- 先把结果跑通

缺点：

- 页面无法显示对应推理图缩略图

### 方式 C：心跳

接口：

```text
POST /api/device/heartbeat
```

作用：

- 告诉页面设备还在线
- 即使暂时没有新图，也不会马上被判定为离线

## 4. 现在支持的五种缺陷类别

现在已经统一成你的题目要求：

- `脏污`
- `折皱`
- `划痕`
- `针孔`
- `擦伤`

系统也兼容一部分老英文标签，会自动映射成上面这五类。

## 5. 推荐的 payload 格式

```json
{
  "timestamp": "2026-05-26T20:00:00+08:00",
  "frame_id": "arm-000123",
  "model_name": "Vision-Defect-Model",
  "board_name": "FPGA ARM Board",
  "inference_ms": 18.4,
  "frame": {
    "width": 1280,
    "height": 720
  },
  "result": "NG",
  "defect_count": 1,
  "detections": [
    {
      "label": "脏污",
      "confidence": 0.96,
      "bbox": {
        "x": 0.42,
        "y": 0.35,
        "w": 0.11,
        "h": 0.09
      }
    }
  ]
}
```

说明：

- `x y w h` 推荐用归一化坐标，也就是 `0~1`
- `result` 建议直接传 `OK` 或 `NG`
- `frame_id` 每帧唯一

## 6. 页面上的“重建实时连接”是什么意思

这个按钮不是“打开一个新页面”。

它的作用是：

- 重新建立浏览器和树莓派之间的 `WebSocket`
- 重新建立浏览器和树莓派之间的 `MJPEG` 流

适用场景：

- 浏览器刚切回来
- 网络抖动
- 实时画面卡住
- 设备重新插拔

所以它本质上是“修复实时链路”的按钮，不是“跳转”按钮。

## 7. 你刚才看到数据一跳一跳的原因

原因主要有两个：

1. 演示脚本按固定间隔不断推新帧，页面会跟着切
2. 当前页是“收到新包就更新”，不是平滑插值动画

这不是错，但如果比赛时想更稳一点，建议：

- 板端按稳定频率推送，比如 `1 fps`、`2 fps` 或固定检测节奏
- 只在完成一帧推理后再上传结果，不要同一帧重复上报
